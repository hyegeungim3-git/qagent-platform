# DECISIONS — 이 프로젝트가 지금 모습인 '이유' (설계 결정 기록/ADR)

> **왜 이 문서가 필요한가.** 코드는 *무엇을* 했는지 보여주지만 *왜* 그렇게 했는지는 보여주지 않는다.
> 커밋 메시지·CLAUDE.md 현재상태는 '무엇을 했나'의 로그다. 이 문서는 그 결정들의 **근거·기각안·결과**를 남겨,
> 다음 모델(무엇이든)이 불변식을 모르고 깨뜨리거나, 이미 폐기한 대안을 재발명하지 않게 한다.
> **읽는 순서:** [CLAUDE.md](../CLAUDE.md) → 이 문서 → [HANDOVER.md](HANDOVER.md) → [DOMAIN-PACK-GUIDE.md](DOMAIN-PACK-GUIDE.md).
>
> 형식: 각 결정은 **맥락 / 결정 / 왜 / 기각한 대안 / 결과(불변식)**. 불변식은 **깨면 안 되는 것**이다.

## ADR-1. 2층 구조: 도메인 중립 코어 + 도메인 팩

- **맥락**: 출발점은 특정 조직(한국부동산원) 전용 데모였다. 다른 발주처에 보여줄 때마다 전체를 복제·치환하는 방식은 유지비가 폭증한다.
- **결정**: 코어(도메인 중립 컴포넌트·로직)와 도메인 팩(`src/domains/*.js`, 순수 콘텐츠)으로 분리. 새 발주처 = **팩 파일 1개 + 레지스트리 등록**.
- **왜**: 이 제품의 본질은 "특정 조직 데모"가 아니라 **"발주처를 갈아끼우는 범용 플랫폼"**이다. 영업 현장에서 "당신 조직으로 바꾸면?"에 3분 안에 답하는 것이 최대 무기다(→ P2 팩 스튜디오가 이걸 노코드로 증명).
- **기각한 대안**: ① 조직별 브랜치/저장소 복제 — 공통 개선이 전 조직에 안 퍼짐. ② 런타임 설정 객체만으로 분기 — 콘텐츠 밀도(시나리오·XAI·세계관)를 담기엔 빈약.
- **결과(불변식)**:
  - 조직·업무 문자열을 코어 파일(UserApp/AgentHub/App/컴포넌트)에 **하드코딩 금지**. 팩 필드로 공급하고 코어엔 REB fallback만.
  - 코어가 팩을 조회할 땐 **리졸버 경유**(`getDomain`/`getDomainList`/`allScenarios`) — `DOMAINS`·`domain.orchestration` 직접 참조 시 커스텀 팩/시나리오가 누락된다(ADR-8).
  - 코어 수정이 필요해 보이면 그건 "팩이 부족"이 아니라 **"코어가 덜 일반화됨"** 신호 → 코어를 일반화하는 커밋과 팩 콘텐츠 커밋을 **분리**한다.

## ADR-2. 백엔드 없음 — 전부 mock 시뮬레이션 (+ 시뮬레이션 정직성)

- **맥락**: 발표·영업용 데모다. 실 백엔드·실 LLM·실 인프라를 붙이면 데모가 불안정해지고 구축 비용이 목적을 압도한다.
- **결정**: 모든 AI 응답·데이터는 mock. 단 **데이터 흐름은 진짜처럼**(라이브 엔진은 규칙 기반 실시간, 감사 로그는 실제 이벤트에서 축적), 랜덤이 아니라 **재현 가능한 규칙**.
- **왜**: 데모의 신뢰는 "살아있음"과 "일관성"에서 온다. 하드코딩된 가짜 결과는 질문 한 번에 무너지지만, 규칙 엔진은 같은 입력에 같은 결과를 낸다.
- **기각한 대안**: 실 LLM 즉시 연동 — 데모 중 타임아웃·환각·비용 리스크. (→ V4 W1에서 **하이브리드**(mock 폴백 있는 실연동)로 승격 설계. mock을 버리지 않는 이유가 이것.)
- **결과(불변식)**: 시뮬 기능엔 "실서비스 대체 지점"을 서사로 남긴다. 새 localStorage 컬렉션은 초기화/리셋 경로에도 등록.

## ADR-3. 완료의 정의 = 빌드 + 실행 증거 (그리고 ASCII 빌드 규칙)

- **맥락**: 이 머신에서 `npx vite build`는 한글 경로(`C:\한국부동산원`) × Tailwind v4 네이티브 모듈 탓에 **"✓ transformed" 직후 조용히 크래시(0xC0000409)**한다. 이 사실을 몰라 **7주간 "빌드 통과"로 오판**했다(2026-07-05 진단).
- **결정**: 완료 판정은 항상 **① 종료 코드 0 + "✓ built in Xs" + dist 갱신**, ② 실행 증거(DOM/측정값/스크린샷), ③ 규모 있으면 verify.mjs·품질게이트. 로컬 빌드는 **ASCII 경로 복사 후** 검증하거나 CI로 갈음.
- **왜**: "될 겁니다"는 이 프로젝트에서 7주짜리 오판을 낳았다. 증거 없는 완료는 완료가 아니다(품질기준-마스터 §2-③).
- **기각한 대안**: 한글 경로에서 직접 빌드하고 "transformed"까지 보고 통과 — **바로 그 함정이다.**
- **결과(불변식)**: "transformed" 라인만 보고 판정 금지. 상세 절차는 [QUALITY-CHECKLIST.md](QUALITY-CHECKLIST.md) §A + [genos-work pitfalls §1](../.claude/skills/genos-work/references/pitfalls.md).

## ADR-4. 세계관(world-building) — 콘텐츠 품질은 양이 아니라 정합성

- **맥락**: 도메인 팩 콘텐츠는 "필드를 채우는 일"로 보이지만, 좋은 데모와 소품의 차이는 밀도가 아니라 **하나의 사건이 여러 화면에서 같은 숫자로 맞물리는가**에서 갈린다.
- **결정**: 각 도메인은 대표 사건 1~2개를 정하고, 모든 필드(suggestions·sampleAnswers·notifications·orchestration·agentRouting·회의록·mapIntel·liveMetric)가 **같은 수치 단일 원장**을 인용하며 **인과적으로 정합**하게 짠다.
- **왜**: 예) 한빛 예지보전 — 회의록의 임계치 하향(4.5→3.5mm/s, 3/20)이 있어야 "RMS 4.2는 구 임계치론 미감지 → 조기 감지 첫 사례"라는 서사가 성립한다. 고립된 콘텐츠는 아무리 잘 써도 데모 중 질문에 모순을 드러낸다.
- **결과(불변식)**: 새 수치를 만들기 전 팩을 grep해 기존 수치를 승계한다. 방법론: [genos-pack 스킬](../.claude/skills/genos-pack/SKILL.md).

## ADR-5. 하네스 우선 — 판단이 필요 없는 검증은 스크립트로 외재화

- **맥락**: 모델이 바뀌어도 품질이 유지되려면, 강한 모델이 "알아서 하던" 검증·함정회피를 **구조로 강제**해야 한다(품질기준-마스터 §0).
- **결정**: 프로젝트 로컬 하네스 — `verify.mjs`(puppeteer-core 헤드리스로 3도메인 금칙어·마커·카드수·콘솔·375뷰포트 자동 판정) + `pitfalls.md`(실사고 전집) + `genos-work` 오케스트레이터 스킬.
- **왜**: **판단이 필요한 곳(콘텐츠 품질)은 원칙·사고이력으로, 판단이 필요 없는 곳(회귀 검증)은 스크립트로.** 스크립트는 모델과 무관하게 같은 답을 낸다 — Fable 5가 없어도 verify.mjs는 똑같이 PASS/FAIL을 판정한다.
- **결과(불변식)**: 새 도메인 팩을 추가하면 `verify.mjs`의 `DOMAINS` 배열에도 판정 기준(금칙어·마커·카드수)을 추가. 새 함정을 밟으면 즉시 `pitfalls.md`에 기록(하네스는 진화한다).

## ADR-6. 상태는 전부 localStorage (백엔드 상태 없음)

- **맥락**: 백엔드가 없으므로(ADR-2) 대화·피드백·감사·커스텀 팩·시나리오·UI 설정을 어딘가 저장해야 한다.
- **결정**: 도메인별 네임스페이스 키(`genos.<기능>.<도메인>`)로 localStorage에 저장. SECURE 탭은 **무저장**(보안 서사).
- **왜**: 데모는 새로고침·재방문에도 상태가 살아있어야 설득력이 있다. 도메인별 분리는 발주처 전환 시 데이터가 섞이지 않게 한다.
- **결과(불변식)**: 새 키를 만들면 관리자 데이터 관리·초기화 경로와 SECURE 제외 규칙을 함께 고려(→ V4 W5가 이걸 통합 관리로 승격). 현재 키: `genos.activeDomain`·`genos.convos.<d>`·`genos.feedback.<d>`·`genos.audit.<d>`·`genos.customPack`·`genos.customScenarios.<d>`·`genos.uiPrefs`.

## ADR-7. 스키마 정본은 문서가 아니라 코드

- **맥락**: 팩·엔진 필드의 shape가 문서(DOMAIN-PACK-GUIDE)와 코드에서 어긋나면 어느 쪽을 믿을지 혼란이 온다.
- **결정**: **스키마 정본 = 코드**. 에이전트 콘텐츠는 각 파일 상단 `CONTENT_DEFAULTS`, 엔진 스키마는 `liveEngine.js` 상단 주석, 팩 필드는 실제 소비 지점. 문서는 안내일 뿐.
- **왜**: 코드가 실제로 실행되는 계약이다. 문서와 코드가 다르면 코드가 맞고, 문서를 고친다.
- **결과(불변식)**: 팩 작성 전 해당 `CONTENT_DEFAULTS`/소비 코드를 먼저 읽는다. 추측으로 필드를 쓰지 않는다.

## ADR-8. 코어의 도메인·시나리오 조회는 리졸버 단일 경로

- **맥락**: 커스텀 팩(P2)·커스텀 시나리오(P4)는 정적 팩 뒤에 localStorage 오버레이로 붙는다. 코어가 `DOMAINS`·`domain.orchestration`을 직접 참조하면 이 오버레이가 **조용히 누락**된다(에러 없이 안 보임 — 최악의 버그 유형).
- **결정**: 도메인 조회는 `getDomain()/getDomainList()`, 시나리오 조회는 `allScenarios(domain)` 단일 경로.
- **왜**: 단일 경로여야 이후 어떤 오버레이(커스텀·실 LLM·다국어)를 추가해도 전 소비처가 자동 반영된다.
- **결과(불변식)**: 새로 도메인/시나리오를 읽는 코드를 쓸 때 반드시 리졸버 경유. 관리자 mocks.js 상수도 유사 계약 — 새 상수는 **`export let`·`__REB_DEFAULTS`·`applyAdminDomain` 3곳 등록**(누락 시 도메인 전환이 조용히 무시됨).
- **승인된 예외 (유일)**: 팩 스튜디오(packstudio.jsx)의 **베이스 팩 선택**은 `DOMAINS` 직접 참조가 맞다 — 커스텀 팩이 자기 자신을 베이스로 삼는 순환을 막으려면 조회 대상이 정식 팩 한정이어야 하기 때문. 이 외의 `DOMAINS[` 직접 참조는 전부 위반이다 (판정: `grep -rn "DOMAINS\[" src | grep -v "domains/index.js" | grep -v packstudio` → 0건).

## ADR-9. 버전 라인 분리 — 과정은 보존, 결과는 동결

- **맥락**: v2까지의 완성본을 보존하면서 v3을 자유롭게 개발해야 한다. 사용자에게 "지금까지의 과정과 결과물"을 남기는 것이 요구.
- **결정**: v2 최종본은 **태그 `v2.0` + 저장소 `reb-ai-platform-v2`**(동결, main이 v2.0 트리로 복원 서빙), v3 개발은 **별도 저장소 `reb-ai-platform-v3`**(origin, base `/reb-ai-platform-v3/`). 과정=git 이력, 결과=태그 체크아웃.
- **왜**: 동결본과 개발본이 같은 URL을 다투면 혼선. 저장소·URL·base를 분리하면 각 버전이 독립적으로 산다.
- **기각한 대안**: `git push --force`로 v2 main 되감기 — 권한 정책상 거부됨 + 이력 파괴. 대신 **commit-tree fast-forward**(현 HEAD를 부모로, 트리만 v2.0인 커밋)로 비파괴 복원.
- **결과(불변식)**: 배포 표([CLAUDE.md §2](../CLAUDE.md))가 정본. push 전 origin이 어느 저장소인지 확인. 동결 판정 마커는 **버전 전용 문자열**로(공통 콘텐츠는 양쪽에 다 있어 오판 — 예: manifest.webmanifest 링크가 P5 전용 증거).

## ADR-10. XAI·감사추적은 "규제 서사를 실동작으로" — 데모의 차별화 축

- **맥락**: AI 플랫폼 데모는 기능 나열로는 차별화가 안 된다. AI 기본법(2026 시행) 대응은 공공·규제 발주처의 실질 관심사다.
- **결정**: 답변마다 신뢰도·근거 구성·'왜 이 답변인가'(XAI), 저신뢰 시 인적 검토 권장(HITL), 오케스트레이션에 판정 기여도·사람 확인 지점, 그리고 이 모든 상호작용을 감사 로그로 축적해 관리자 AI기본법 대시보드에 **실데이터로** 표시.
- **왜**: "AI 기본법 제34조 기록·감독"을 mock 지표가 아니라 사용자 실사용에서 쌓이는 실측으로 보여주면 "이건 데모가 아니라 파일럿" 인상을 준다. 피드백 루프·감사추적이 사용자단→관리자단 실데이터 흐름의 완결.
- **결과(불변식)**: 새 상호작용 유형은 감사 로그 이벤트로 이어붙일 수 있는지 고려. SECURE 세션은 항상 로그 제외.

## 이 프로젝트를 '다시 만든다면' 지킬 순서 (재현 요약)

1. **2층 구조부터**(ADR-1) — 코어/팩 분리를 첫 커밋에. 나중에 분리하려면 하드코딩을 걷어내야 해서 몇 배 비싸다.
2. **하네스를 초반에**(ADR-5) — verify.mjs·pitfalls를 기능 3~4개 시점에 만든다. 늦게 만들면 회귀가 쌓인 뒤라 신뢰가 안 선다.
3. **세계관 먼저, 필드는 나중**(ADR-4) — 대표 사건과 수치 원장을 정하고 필드를 채운다.
4. **완료는 증거로**(ADR-3) — 빌드 판정 규칙을 프로젝트 CLAUDE.md 최상단에.
5. 나머지(상태 저장·리졸버·규제 서사)는 기능이 커지며 ADR-6·8·10 순으로.
